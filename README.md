**astrbot_plugin_weibo_forward_to_qqgroup** —— 一个 AstrBot 插件：**无需微博账号 Cookie**，实时轮询监控指定微博博主，新微博自动推送到绑定的 Q 群；微博视频以 QQ 视频消息直接转发（群里可直接播放），图片可自动上传到群相册（不同博主可绑定不同相册，实况图自动转 GIF），推送消息可附带图片。内置 WebUI 控制面板。

## 功能特性

- **完全免 Cookie**：自动向微博游客系统换取并维护匿名游客身份，开箱即用，不需要登录微博、不需要抓包提取 Cookie。
- **准实时监控**：默认 120 秒轮询一次（最小 30 秒），发现新微博即时推送；两次检查之间积压超过一页时自动翻页补漏，不漏博。
- **群绑定制**：在目标群聊里发一条 `微博绑定` 即完成接入，支持同时绑定多个群。
- **转发也推**：博主转发别人的微博同样推送（标注 `转发 @原作者`，可配置只推原创）。
- **图片自动进群相册**：按博主绑定相册，转发成功后自动上传 `/large/` 原图；实况图转 GIF；台账去重防重复上传。
- **推送消息带图**：附 `mw2000` 轻量档图片（长边 2000px），有张数上限防刷屏。
- **视频直接转发**：微博内嵌视频（纯视频帖 / 图文混排 / 转发原微博）下载后以 QQ 视频消息发送，群里可直接播放；自动选清晰度档位，视频消息被协议端拒收时自动改发**文件消息**（默认按临时文件发，手机上点接收即可下载，不占群文件配额），再不行才降级为原帖链接提示。
- **推送重试**：QQ 掉线等原因导致发送失败时自动重试，恢复后补推；已发送条目即时落盘，重载 / 崩溃不重发。
- **风控自愈**：432 全局冷却、游客身份自动换新、请求间隔与指数退避，长期无人值守稳定运行。
- **免刷屏**：首次添加账号只建立基线，不会把历史微博倒灌进群。
- **WebUI 控制面板**：运行状态、推送统计、最近动态一览，并可直接增删博主 / 推送目标 / 相册规则、手动触发检查。

## 安装

> 仓库根目录即插件本体（`metadata.yaml`、`main.py`、`_conf_schema.json` 都在顶层），依赖仅 `aiohttp`（AstrBot 已内置），装好后无需额外配置。

**方式一：WebUI 从仓库安装（推荐）**

在 AstrBot WebUI「插件」页选择「从仓库安装」，填入：

```
https://github.com/diyushuang/astrbot_plugin_weibo_forward_to_qqgroup
```

**方式二：上传 zip**

在 WebUI「插件」页上传发布包 `astrbot_plugin_weibo_forward_to_qqgroup-vX.Y.Z.zip`。自打包时沿用发布包结构：zip 内放一层同名文件夹。

**方式三：手动放置**

把仓库内容（不含 `.git`）复制到 `data/plugins/astrbot_plugin_weibo_forward_to_qqgroup/`，然后在 WebUI「插件」页重载 / 启用。

## 升级

**AstrBot ≥ v4.28.2**：WebUI 上传新版本 zip 直接覆盖（自动备份，失败自动恢复）。

> v4.28.0 / v4.28.1 上传同名 zip 会报「目录已存在」，属该版本限制，请先升级 AstrBot 或用下面方式。

**任何版本通用**：WebUI「插件」页卸载旧版本（**不要勾选「删除配置」**）→ 上传新版本 zip。

**推荐长期使用**：用方式一从仓库安装，此后每次升级只需点插件列表的「更新」。

**数据不会丢失**：配置存于 `data/config/astrbot_plugin_weibo_forward_to_qqgroup_config.json`，运行状态存于 `data/plugin_data/astrbot_plugin_weibo_forward_to_qqgroup/state.json`，均不在插件目录内。

> **⚠️ v1.4.1 起插件改名（破坏性）**：标识由 `astrbot_plugin_weibo_monitor` 改为 `astrbot_plugin_weibo_forward_to_qqgroup`。配置与状态按插件名寻址，装新版等于全新安装：绑定的群、监控账号、相册规则需重新添加，且请**先卸载旧插件**——两个插件同时轮询同一批账号会使请求量翻倍、更易触发风控，群里也会收到重复推送。首次运行只建立基线，不会倒灌历史微博。

## 快速开始

1. 在要接收推送的 Q 群里（管理员账号）发送：

   ```
   微博绑定
   ```

2. 添加要监控的博主（纯数字 uid 或主页链接均可）：

   ```
   微博添加 1234567890
   微博添加 https://weibo.com/u/1234567890
   ```

   uid 获取：打开博主微博主页，地址栏 `weibo.com/u/数字` 中的数字即 uid。

3. 完成。之后博主一有新微博，群里就会收到：

   ```
   📢 微博更新
   【昵称】10-03 21:30
   正文摘要……
   🔗 https://weibo.com/1234567890/XXXXXXX
   ```

4. （可选）让某博主的微博图片自动上传到本群相册：

   ```
   微博相册绑定 1234567890 美食图集
   ```

   相册名称与 ID 可用 `微博列相册` 查看，详见[群相册自动上传](#群相册自动上传)。

## 群相册自动上传

**使用**

1. 在目标群内绑定：`微博相册绑定 <uid> <相册名或ID>`（同一博主可在不同群绑不同相册）；
2. 该博主有新微博且**成功推送到该群**后，插件自动提取微博内全部图片（含转发原微博的图）；
3. 下载 `/large/` 原图到临时目录 → 经 NapCat 的 OneBot 扩展接口 `upload_image_to_qun_album` 传进相册 → 传完即删临时文件；
4. 实况图（livephoto）优先转 GIF 上传（需 ffmpeg），失败或 GIF 超 30MB 回落封面静图；纯视频微博跳过（群相册只收图片与实况图）。

**防重复**：按「微博图片 pid」记录上传台账（KV 存储，保留 30 天、每相册上限 2000 条），插件重启、重发同一条微博都不会重复上传。开启 `album_same_host` 时额外回读相册已有文件名比对；默认的 base64 载荷会被协议端改名（文件名里没有 pid），因此不做回读——它每次要串行翻最多 8 页媒体列表。

**关键词路由**（v1.7.0）：除了按博主绑定，还可以按微博内容路由——

```text
微博关键词相册 福利 1234567890 福利图集          # 全局规则：任何博主命中「福利」都生效
微博博主关键词相册 7448216742 福利 1234567890 福利图集   # 博主规则：只对该博主生效
```

命中关键词的微博图片**只**上传到规则指定的固定群相册（替代该次的所有默认绑定），消息推送不受影响。匹配范围与屏蔽词一致（正文 + 转发原文，子串包含）；博主规则优先于全局规则，各自按配置顺序第一条命中生效；未配置或均未命中时完全按默认相册绑定上传，行为与老版本一致。

**频控与资源保护**（口径对齐 astrbot_plugin_weibo_album）：下载并发（默认 5）、上传并发（默认 3）、张间隔（默认 0.5 秒）、在途载荷字节预算（默认 32MB，超预算自动排队，相当于按体积自动降低并发）、ffmpeg 转码 CPU 总闸（全局最多同时 2 个）、批次下载前的磁盘余量保护线（1GB）六层闸门，全部全群共享——多个群同时触发也不会叠加资源峰值。实况图 GIF 产物超 30MB 自动回落封面静图，避免超大 GIF 的 base64 载荷把小内存服务器顶穿。

**诊断文件**：每批下载 / 上传在重负载动作**之前**，把「张数 / 总体积 / GIF 张数 / 并发与预算配置」写入 `data/astrbot_plugin_weibo_forward_to_qqgroup/diagnostic.log` 并立即刷盘（超 512KB 自动只留后半段）。整机被内存顶死时主日志往往来不及落盘，重启后读这份文件即可还原死机前最后几批的状态，无需复现。

**前置条件**

- QQ 侧使用 NapCat ≥ v4.8.101（旧版没有群相册扩展接口，上传时会明确报「不支持的API」）；
- 相册需先在 QQ 里手动创建好，`微博列相册` 可查看本群全部相册的名称与 ID；
- 只有绑定规则所在**群**推送成功才触发上传：请确认该群已 `微博绑定`。

**上传失败怎么办**：失败原因记录在 AstrBot 日志（常见：相册被删、机器人权限不足、QQ 相册网关临时 502），每批的张数、体积与下载 / 上传耗时在同一处。同一批图片不会自动重传（避免重复上传风险）；个别缺失的图片可用相册类插件对单条微博链接手动补传——两个插件的台账互相独立，手动补传时留意相册里多出重复。

## 视频转发

开启 `message_with_videos` 后，检测到视频的微博会提取视频直链，下载到本地临时目录后以 **QQ 视频消息**发送（群里点开即可播放），发完即删临时文件。直链优先取时间线卡片自带的 `page_info.media_info`（实测 m.weibo.cn 已经把可用 mp4 档给到了卡片里，12/12 样本与详情接口一致），卡片里取不到才补一次 `statuses/show` 详情请求——密集发博的账号每轮可省下若干个 2~5 秒限速的微博请求，也少一个可能被风控的失败点。

**覆盖范围**：纯视频帖、图文混排帖（mix_media_info 里的视频与图片都会带上）、转发原微博带视频的帖子。直播中的视频暂不支持（自动降级为链接提示）。

**清晰度与体积**：优先取微博多码率数组中的 mp4 档（`video_quality` 选档，失败自动尝试其它档位与旧版字段回退链，含 `media_info.urls` 里的 `mp4_hd_mp4` / `mp4_720p_mp4` / `mp4_ld_mp4` 档位表；base64 内嵌发送时会优先挑体积适配上限的最高清晰度档位，1080p 超帽自动落 720p/流畅档）。QQ 视频消息硬上限 100MB，`video_max_mb` 默认 95MB 留出余量；超限的视频**连一个字节正文都不下载**（按响应头声明的体积当场判超限，换下一档或直接降级），失败原因（超上限 / HTTP 状态 / 磁盘余量…）记在面板的「视频未转发」条目上，不再只留一句「未能自动转发」。

**内嵌体积上限（`video_inline_max_mb`，默认 30MB）**：base64 内嵌一路上是文件体积 5~6 倍的瞬时内存（编码串 + JSON 序列化 + 传输缓冲，插件与协议端两侧各来一遍），大视频会把小内存服务器顶到无响应——这也是「服务器卡死 → 发送超时重发 → 群里重复收到同一消息 → 相册上传成批失败」这条事故链的根因。超过上限的视频自动降级为链接提示；未配置 `callback_api_base` 时下载上限也会同步取 `video_max_mb` 与本项中较小者。大视频刚需的部署请配置 `callback_api_base` 走路径直传（无内存放大，本项不生效）。

**为什么必须先下载**：微博视频 CDN 校验 Referer 防盗链（实测无 Referer 直接 403）且直链带签名会过期，不能像图片那样把链接丢给协议端自己抓。插件下载时已带正确的 Referer 与 UA。

**视频消息被拒收时的兜底（`video_file_fallback`，默认开）**：QQNT 对富媒体（图片 / 视频消息）的拒收回执是 `rich media transfer failed`（retcode 1200），而这句话**既可能是素材真的超限，也可能是协议端自己的毛病**（NapCat 版本回归、账号风控）——2026-10-09 那条线上事故就是后者：一条 **5.6MB / 120 秒** 的微博视频被判「富媒体超限」，离 100MB 硬限差了一个量级。QQ 的**文件服务**走的是另一条上传通道，所以现在命中这个回执时双管齐下：

- 正文（含图片）照常送达：视频段从消息里摘掉，不占用 `max_pending_retries` 配额，提示语见下；
- 视频本身改以**文件消息**发到**每个**目标群（`upload_group_file`，base64 内嵌载荷、不依赖任何路径映射，分离部署同样可用；文件名 `微博_<微博ID>.mp4`，多视频带 `_1` `_2` 序号）——群里出现一条文件消息，成员点接收即可下载。

**落点由 `video_file_temp` 决定（默认临时文件）**：

- **开（默认）**：NapCat 以 `upload_file=false` 发**临时（在线）文件**——视频**不会**进群文件列表，因此**不占**群文件的 10GB / 1500 个文件配额；代价是成员要手动点接收（群里那条文件消息保留在聊天记录里，但没人接收/转存的话，服务器中转只留一段时间就失效）。
- **关**：不带该参数（NapCat 默认行为）⇒ 视频落进**群文件永久空间**：可在线播放、长期留存、随时能翻出来，但要吃配额；群文件空间满时 QQ 会自己把新文件降级成临时件（10 天左右），并且 NapCat 有已知问题会直接报错导致上传失败（Issue #1466）。
- 旧版 NapCat 不认识 `upload_file` 字段时会忽略它、退回「进群文件」，属于安全降级。

顺序是**先把视频送进群、再发正文消息**，所以正文尾部那句说明总是与真实结果一致：全部目标群都送成了才说"已改以文件消息发送"（临时文件模式）或"已改以群文件发送"（永久模式），否则退回「🎬 视频未能自动转发，请点原帖链接观看」（代价是正文要等这一次上传，单次上传最长 180 秒）。同一轮里反复发不出去（例如一直超时）的条目，在超过 `max_pending_retries` 做最后的去视频降级之前，也会先走这条兜底。

文件发送失败不影响正文送达（机器人没有群文件上传权限、群禁用了文件、临时文件已被清理、超时等），失败原因与协议端回执一并记在面板待推送队列、最近动态与错误留存里。**体积帽**：这条兜底固定走 base64 内嵌（插件写不出 NapCat 那台机器上的路径），所以它**单独按 `video_inline_max_mb` 判一次帽**——配了 `callback_api_base` 的部署里视频消息走路径直传、内嵌上限本来不生效（几十 MB 的视频照进链），不另设帽的话兜底自己就成了把小内存服务器顶死的那个；超帽的视频跳过兜底、如实报因，群里退回提示链接，正文不受影响。不需要视频落群文件的部署把 `video_file_fallback` 关掉即可回到旧口径。

**签名过期与自愈**：直链的签名有效窗实测约 **3600 秒**。跨轮次重试、插件重载（WebUI 保存配置即触发，会清空 `video_tmp`）后，条目里挂着的都是旧链，拿去下载必然 403——所以下载前会先检查直链年龄，过窗就重新提取一次；下载中途撞到 403/404 也当场重取新链重试同一档。一轮失败不再把这条视频永久判死：最多试 `3` 轮（轮与轮之间隔一个轮询间隔，每轮都带新链），耗尽才落「🎬 视频未能自动转发」提示。超上限这类确定性失败会**当场定论**，不空等后续轮次。

**部署形态**：

- **任意形态开箱即用**：视频段默认以 base64 内嵌发给协议端（与图片同一条路），NapCat 在 Docker / 与 AstrBot 分容器部署（互相看不到对方文件系统）时无需任何路径映射或额外配置。v1.6.0 那种「分离部署必现 ENOENT、整条推送失败」的问题从根上消除。
- **配置了 AstrBot `callback_api_base`**：改走本地路径，由 AstrBot 把文件注册成回调下载链接交给协议端取文件，省掉 base64 的内存放大（要求 NapCat 能访问该回调地址）。大视频、内存紧张的部署建议配置。
- **同机 / 共享文件系统**：默认同样走 base64（多一次瞬时内存开销但一定可达）；想省内存就配上 `callback_api_base`。

**资源保护**（与群相册上传并存不叠加峰值）：视频下载与相册图片下载共用同一并发闸；下载前过磁盘余量保护线（1GB）；64KB 分块流式落盘，下载不把视频读进内存；发送时 base64 内嵌的体积受 `video_inline_max_mb`（默认 30MB）封顶，超限自动降级链接提示，内存紧张可进一步调低或配 `callback_api_base` 走路径直传；临时文件在推送成功 / 放弃 / 过期三个出口都会立即删除，启动与关停时清空 `video_tmp`；发送超时按「结果未知」处理——整条不再重发以防重复（大载荷超时多半是实际已送达），相册图片照常上传；发送前会打「已开始发送」戳并落盘，崩溃 / 重载后带戳条目跳过重发，杜绝「重启后整批重发一遍」；视频段反复发送失败时，重试超限前会去掉视频段降级重发，正文和图片保底出群。

## WebUI 控制面板

无需记忆指令：**AstrBot 管理面板 → 插件 → 微博实时转发 → 详情页 → 打开页面**（插件页面由 Dashboard 内嵌加载，无需额外端口与认证配置）。

**展示**：轮询任务与下次检查时间、待推送队列（含重试、「含视频」「发送中」「视频未转发」标记，视频没转发时会直接显示**失败原因**；被协议端拒收过的条目另显示**协议端回执、当时体量与视频去向（改发临时文件 / 进群文件 / 只剩提示链接）**，见[常见问题](#常见问题)）、风控冷却剩余、身份模式与年龄、出网方式（凭据打码）、**服务器内存与磁盘余量**（内存低于 512MB 红色告警——历史「服务器无响应」事故均为内存顶穿，死机前最后一眼面板就有余量）、后台任务在途数（视频下载 / 相册上传）、监控博主（昵称 / 已见数 / 失败退避 / 推送数）、推送目标与相册规则、推送统计（近 7 天柱状图 / 博主排行）、最近动态时间线（含「视频未转发」条目）、**错误日志留存**。

**错误日志留存**：本插件所有 warning/error（发送超时、检查失败、相册上传失败、风控冷却、后台任务异常）在产生的瞬间写入 `data/astrbot_plugin_weibo_forward_to_qqgroup/errors.log`（JSONL 逐条 fsync，512KB 自动轮转）并在面板「错误日志留存」卡片展示，服务器崩溃 / 无响应后重启仍能看到出事前的最后记录（带「上次运行」标记）；支持一键清空。

**操作**：一键「立即检查」、清空错误日志留存、增删监控博主、增删推送目标、增删相册规则。

页面数据每 20 秒自动刷新（页面切到后台即暂停），跟随面板明暗主题；Cookie 值与代理凭据不会回显。所有变更与聊天指令写入同一份配置，立即生效。插件空闲时（无新微博、面板未打开）没有任何定时器、后台线程或磁盘写，唯一的周期性开销是轮询本身的每账号一次时间线请求。

> 需要较新版 AstrBot Dashboard 支持插件页面；旧版只是看不到页面，插件本体不受影响，`微博状态` 末行会提示面板是否已启用。

## 工作原理

插件**不使用、也不需要**你的微博账号 Cookie。m.weibo.cn 的时间线接口要求一个「游客身份」，插件自动向微博游客系统（`visitor.passport.weibo.cn`）完成经典的 `genvisitor → incarnate` 流程，把匿名游客 Cookie（SUB/SUBP，种在 `.weibo.cn` 域）维护起来，全程无需登录、无需人工干预：

1. 首次请求前自动预热 `m.weibo.cn` 并换取游客身份；
2. 每轮向 `https://m.weibo.cn/api/container/getIndex?type=uid&value={uid}&containerid=107603{uid}` 请求第一页微博；整页都是未见微博时自动翻页补漏（最多共 3 页）；
3. 与本地已见 ID（`state.json`，按加入顺序保存、上限 500 条、只淘汰最早记录）比对去重，新微博按「旧→新」顺序推送到所有绑定会话，发送成功即出队落盘；
4. 遇到 `ok=-100` / HTTP 418/432 / JSON 接口返回 HTML 拦截页（游客身份过期或风控）时自动换新游客身份并重试一次，触发风控则进入全局冷却；游客身份最长复用 3 天，到期主动更新并持久化到本地。

## 稳定性与风控对策

针对微博对游客访问的限流与反爬机制（432 自定义风控码：游客身份过期、请求频率 / 累计量超阈值、IP 信誉三类因素叠加），插件内置以下对策：

| 措施 | 说明 |
| --- | --- |
| 游客身份先行 | 所有请求前确保持有游客 Cookie（与 RSSHub 2025-11 对同一接口的修复方案一致） |
| 续期节制 | 游客身份有效期数天，但频繁调用游客接口本身是风控信号：非失效不续期（复用 3 天）、换新间隔 ≥10 分钟、每小时最多 3 次、失败指数退避 |
| 全局请求间隔 | 任意两次微博请求之间强制 2~5 秒随机间隔，杜绝突发并发 |
| 432 全局冷却 | HTTP 418/432 属于 IP 级风控，触发后全局暂停所有微博请求（10 → 30 → 60 分钟梯度升级），期间不消耗推送重试次数；冷却期内重复触发不叠加升级，距上次触发超过 2 小时梯度自动重置；成功一次即解除。JSON 接口返回 200 + HTML 拦截页同样按风控处理 |
| 指纹一致性 | UA 与游客身份绑定（一套身份一套指纹），均为移动端 UA，配合 Referer / MWeibo-Pwa / X-Requested-With / XSRF 头保持浏览器式一致性 |
| 启动预热 | 重启后先访问一次 m.weibo.cn 主页刷新 `_T_WM` / XSRF-TOKEN 指纹，模拟浏览器会话恢复 |
| 账号级退避 | 单账号连续失败时指数退避（1 → 10 分钟），不拖累其他账号 |
| 代理出网 | 海外 / VPS 的 IP 段最易被风控，可配置 `proxy` 走国内出口；家用宽带直连即可 |

## 已知限制

- 匿名游客身份大约可见 95% 的微博，个别受限微博（仅粉丝可见、部分限流内容）拉取不到，属微博匿名访问的固有限制；如需 100% 覆盖可填写 `custom_cookie`（失效时需自行更换）。
- 免 Cookie 方案依赖微博游客接口的稳定性，若微博调整反爬策略导致持续失败，请关注插件更新。
- 触发 IP 级风控（HTTP 432）时插件自动进入全局冷却（最长 1 小时），期间不产生微博请求，属预期的自我保护行为，可用 `微博状态` 查看。
- 推送到多个群时，任一群成功即视为推送成功，不做按群粒度的重试。
- 置顶微博不推送（避免置顶内容反复提醒）；置顶解除后会正常检测。
- 群相册上传仅支持 NapCat 协议端（≥ v4.8.101）；纯视频微博不上传图片；相册上传失败不做自动重传，缺失图片可手动补传。
- 消息里的图片由协议端远程抓取，QQNT 对像素尺寸/体积超限的富媒体（超长截图、超大原图、超限视频）会**连带拒收整条消息**，NapCat 回 `rich media transfer failed`（retcode 1200）。这类报错原样重发多少轮都是同一个结果，所以插件命中后当场按嫌疑顺序摘段补发：先去掉图片段只发正文（尾部附说明），摘了图仍被拒说明凶手是视频段——去掉视频段并把图片段放回来再发（图片此时还没被证明有罪），两段都撞过才彻底只发正文。**摘掉视频段时视频本身会被改以文件消息发送**（`video_file_fallback`，默认临时文件，见[视频转发](#视频转发)），视频不会因此丢掉。摘段结论记在该条待推送项上，本轮其余会话与后续轮次都不再带那一段，也不占用 `max_pending_retries`；群相册的原图上传走另一套接口，不受影响，图片照样进群相册。
- **被拒时怎么判断是"素材超限"还是"协议端的毛病"**：`rich media transfer failed` 是 NapCat 富媒体通道的通用失败回执，两种成因共用同一句话。插件把现场证据一并留下来——**回执摘要**（`retcode` / `result` / `errMsg`）、**被判罪段当时的真实体量**（视频按落盘文件 MB 数算，图片报张数）、**被拒次数**，三处可查：面板**待推送队列**的「拒收详情」说明（条目还在队里时）、**最近动态**的推送记账（条目出队后回溯）、**错误留存**里的告警行。判读口径：回执是 `rich media transfer failed` 而体量**远低于** `video_max_mb` / `video_inline_max_mb`（例如 5MB 的视频被判超限），问题就在协议端（NapCat 版本回归、账号风控等），去升级 NapCat 或换号，**不要**去调体积上限——视频本身已经由文件兜底送进群了；反之体量贴着上限，才考虑压缩或降档。
- **群里只看到「视频已改以文件消息发送」但没有视频消息**：这是预期的兜底路径（协议端拒绝了视频消息，见上一条）。群里那条文件消息点「接收/下载」就能拿到视频（默认是临时文件，及时接收或转存，别放太久）；文件名是 `微博_<微博ID>.mp4`，可对着原帖链接核对。想让视频长期躺在群文件里、能直接在线播放，把 `video_file_temp` 关掉。如果连文件都没发出去，面板会写明原因（多半是机器人没有上传权限，把机器人设为群管理员或在群设置里放开文件上传即可）。
- `max_pending_retries`（默认 5 轮）只用来兜住网络抖动、协议端重启这类瞬时故障。超限后停止整条重发：条目还带着视频段时先去掉视频段补发一次，并按**真实结果**记账——降级消息真发出去了记推送成功（面板与群里一致，群相册照常上传），一条都没出去才记「放弃推送」。
- 视频转发依赖协议端对 OneBot v11 `video` 消息段的支持（NapCat / Lagrange 群聊均可）；QQ 视频消息硬上限 100MB；直播中的视频与直播回放不支持。NapCat 部分版本存在发视频报 `rich media transfer failed (result: -1)` 的回归，遇到时请升级 NapCat；在升级之前，插件的**文件兜底**（`video_file_fallback`，默认开）会把视频改以文件消息送进群，视频不会因为协议端这条通道坏掉而丢掉。分离部署开箱即用（视频以 base64 内嵌发送，无需路径映射配置）；配置 `callback_api_base` 可改走路径直传以省内存，见[视频转发](#视频转发)。

## 开发

代码风格由仓库根目录的 `ruff.toml` 统一约定（行宽 100、目标 Python 3.10、启用 E/F/W/I/UP/B/SIM/RUF 规则集）。提交前建议跑一遍：

```bash
ruff check .          # 静态检查
ruff format --check . # 格式校验（自动修复去掉 --check）
```

`bench/` 下是离线回归脚本（stub 掉 AstrBot 依赖即可运行），改动推送链路后请至少跑通与改动相关的用例：

```bash
python bench/_test_video_chain.py         # 视频候选/过窗/判死
python bench/_test_video_file_fallback.py # 视频消息被拒收后的文件兜底（临时/永久两种落点）
python bench/_test_pic_reject.py          # 图片拒收与摘段补发
python bench/_test_rich_media_ladder.py   # 摘段升级顺序与拒收回执留档
python bench/_test_v163_errorlog.py       # 错误留存与轮转
python bench/test_dashboard_api.py        # 面板 API
```
