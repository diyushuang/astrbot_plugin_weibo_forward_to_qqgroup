# astrbot_plugin_weibo_monitor

微博实时转发（AstrBot 插件）：**无需微博 Cookie**，实时轮询监控固定几个微博账号，有新微博自动把「昵称 + 摘要 + 链接」推送到绑定的 Q 群；并可将微博内的图片**自动上传到群相册**——不同博主可绑定不同相册，实况图自动转 GIF，推送消息可附带图片（`mw2000` 轻量档，原图进群相册）。

## 功能特性

- **完全免 Cookie**：插件自动向微博游客系统换取并维护匿名游客身份，开箱即用，不需要登录微博、不需要抓包提取 Cookie。
- **准实时监控**：默认 120 秒轮询一次（可调，最小 30 秒），发现新微博秒级推送。
- **群绑定制**：在目标群聊里发一条 `微博绑定` 即完成接入，支持同时绑定多个群。
- **转发也推**：博主转发别人的微博同样推送（原微博的图也会进相册），并标注 `转发 @原作者`（可配置关闭，只推原创）。
- **图片自动进群相册**：按博主绑定相册（`微博相册绑定`），新微博的图片在转发成功后自动上传；原图 `/large/` 直链、实况图转 GIF（需 ffmpeg，缺失回落封面）、台账去重防重复上传。每批的下载/上传耗时与体积都记在日志里。
- **推送消息带图**：推送消息在文本后附带微博图片（可关闭），图片数有上限防刷屏。消息里用的是 `mw2000` 轻量档（长边 2000px）：消息图片由协议端自己远程抓取，塞原图容易把发送顶到超时并触发重复推送；原图仍然只进群相册那条路。
- **推送重试**：QQ 掉线等原因导致发送失败时自动重试，恢复后补推。
- **风控自愈**：432 全局冷却、游客身份自动换新、请求间隔与指数退避，长期无人值守稳定运行。
- **免刷屏**：首次添加账号只建立基线，不会把历史微博倒灌进群。
- **WebUI 可配置**：轮询间隔、摘要长度、是否含转发、相册规则等全部可在 AstrBot 插件配置面板调整。

## 安装

1. 将本目录（`astrbot_plugin_weibo_monitor/`）放入 AstrBot 的 `data/plugins/` 目录；
   或在 AstrBot WebUI「插件市场 → 从仓库安装」填入本插件仓库地址。
2. 在 WebUI「插件」页面重载/启用插件。
3. 安装依赖：AstrBot 会自动安装 `requirements.txt`（仅 `aiohttp`，AstrBot 本身已内置）。

要求 AstrBot ≥ v4.9.2（上传台账使用 KV 存储，已通过 `metadata.yaml` 的 `astrbot_version` 声明，旧版本会明确提示不兼容），QQ 侧使用 aiocqhttp 适配器（NapCat、Lagrange 等）。

## 升级

**方式一：AstrBot ≥ v4.28.2** —— 直接在 WebUI 上传新版本 zip 即可覆盖升级（自动备份旧目录，更新失败会自动恢复旧版本）。

> 注意：v4.28.0 / v4.28.1 上传同名 zip 会报「安装失败：目录 astrbot_plugin_weibo_monitor 已存在」，这是 AstrBot 该版本的限制。请先升级 AstrBot，或用方式二。

**方式二：先卸载再上传（任何版本通用）**

1. WebUI「插件」页卸载旧版本，**不要勾选「删除配置」**；
2. 上传新版本 zip。

**数据不会丢失**：插件配置存于 `data/config/astrbot_plugin_weibo_monitor_config.json`，运行状态（已见微博、游客身份、待推送队列）存于 `data/plugin_data/astrbot_plugin_weibo_monitor/state.json`，均不在插件目录内，上述操作不影响。

**方式三（推荐长期使用）：仓库安装** —— 把插件推送到 GitHub 仓库后，用 WebUI「从仓库安装」安装，此后每次升级只需点击插件列表的「更新」按钮。

## 快速上手

1. 在要接收推送的 Q 群里（由 AstrBot 管理员账号）发送：

   ```
   微博绑定
   ```

2. 添加要监控的博主（支持纯数字 uid 或主页链接）：

   ```
   微博添加 1234567890
   微博添加 https://weibo.com/u/1234567890
   ```

   uid 获取方法：打开博主微博主页，地址栏 `weibo.com/u/数字` 中的数字即 uid。

3. 完成。之后博主一有新微博，群里就会收到：

   ```
   📢 微博更新
   【昵称】10-03 21:30
   正文摘要……
   🔗 https://weibo.com/1234567890/XXXXXXX
   ```

   （默认推送消息附带微博图片，`mw2000` 轻量档，可用配置 `message_with_images` 关闭）

4. （可选）让某博主的微博图片自动上传到本群相册：

   ```
   微博相册绑定 1234567890 美食图集
   ```

   之后该博主的新微博推送成功后，图片会自动传进本群的「美食图集」相册。不同博主可绑不同相册；相册名称与 ID 可用 `微博列相册` 查看。详见下文[「微博图片自动进群相册」](#微博图片自动进群相册)。

## 微博图片自动进群相册

v1.4.0 起支持把微博图片自动上传到 QQ 群相册（能力来自同类项目 astrbot_plugin_weibo_album 的实践方案，已内嵌整合，无需再装另一个插件）。

**工作方式**

1. 在目标群内绑定：`微博相册绑定 <uid> <相册名或ID>`（同一博主可在不同群绑不同相册）；
2. 该博主有新微博且**成功推送到该群**后，插件自动提取微博内全部图片（含转发原微博的图）；
3. 下载 `/large/` 原图到临时目录 → 通过 NapCat 的 OneBot 扩展接口 `upload_image_to_qun_album` 传进相册 → 传完即删临时文件；
4. 实况图（livephoto）优先转 GIF 上传（需服务器安装 ffmpeg），失败回落封面静图；纯视频微博跳过（群相册接口仅支持图片）。

**防重复**：按「微博图片 pid」记录上传台账（KV 存储，保留 30 天、每相册上限 2000 条），插件重启、重发同一条微博都不会重复上传。开启 `album_same_host`（本地路径传图，相册里保留图片名）时，额外回读相册已有文件名比对，挡住手动或其他插件传过的图；默认的 base64 载荷会被协议端改名，文件名里没有 pid，因此不做这个回读——它每次要串行翻最多 8 页媒体列表，白白多花几秒。

**频控保护**：上传并发（默认 3）+ 张间隔（默认 0.5 秒）+ 在途载荷字节预算（默认 32MB）三层限制，不拖垮小服务器、不触发 QQ 相册频控。并发数默认值就是这么定的：协议端传相册是每张内部串行发 16KB 分片，单张本身就慢，同时在传的张数基本等于吞吐。

**前置条件**

- QQ 侧使用 NapCat 协议端，版本 ≥ **v4.8.101**（旧版没有群相册扩展接口，上传时会明确报「不支持的API」）；Lagrange 等其他协议端暂不支持群相册接口。
- 实况图转 GIF 需要运行 AstrBot 的服务器装有 `ffmpeg`（`PATH` 中可找到即可）；未安装时实况图自动改传封面静图，不影响其余功能。
- 相册需先在 QQ 里手动创建好；`微博列相册` 可查看本群全部相册的名称与 ID。
- 只有绑定规则所在**群**推送成功才触发上传：请确认该群已 `微博绑定`（`微博相册列表` 会对未绑定的群给出提示）。

**上传失败怎么办**：失败原因会记录在 AstrBot 日志里（常见：相册被删、机器人权限不足、QQ 相册网关临时 502），每批的张数、体积与下载/上传耗时也在同一处。同一批图片不会自动重传（避免重复上传风险）；个别缺失的图片可用相册类插件（如 astrbot_plugin_weibo_album 的 `/传图`）对单条微博链接手动补传——两个插件的台账互相独立，默认载荷下相册文件名里没有微博 pid，本插件不会因为对方传过就跳过，手动补传时留意相册里多出重复。

## 稳定性与风控对策

针对微博对游客访问的限流与反爬机制（432 自定义风控码：游客身份过期、请求频率/累计量超阈值、IP 信誉三类因素叠加），插件内置以下对策：

| 措施 | 说明 |
| --- | --- |
| 游客身份先行 | 所有请求前确保持有游客 Cookie（与 RSSHub 2025-11 对同一接口的修复方案一致） |
| 续期节制 | 游客身份有效期数天，但频繁调用游客接口本身是风控信号：非失效不续期（复用 3 天）、换新间隔 ≥10 分钟、每小时最多 3 次、失败指数退避 |
| 全局请求间隔 | 任意两次微博请求之间强制 2~5 秒随机间隔，杜绝突发并发 |
| 432 全局冷却 | HTTP 418/432 属于 IP 级风控，触发后全局暂停所有微博请求（10 → 30 → 60 分钟梯度升级），期间不消耗推送重试次数；冷却期内重复触发不叠加升级，距上次触发超过 2 小时梯度自动重置；成功一次即解除 |
| 指纹一致性 | UA 与游客身份绑定（一套身份一套指纹），均为移动端 UA，配合 Referer / MWeibo-Pwa / X-Requested-With / XSRF 头保持浏览器式一致性 |
| 启动预热 | 重启后先访问一次 m.weibo.cn 主页刷新 `_T_WM`/XSRF-TOKEN 指纹，模拟浏览器会话恢复 |
| 账号级退避 | 单账号连续失败时指数退避（1 → 10 分钟），不拖累其他账号 |
| 代理出网 | 海外/VPS 的 IP 段最易被风控，可配置 `proxy` 走国内出口；本机家用宽带直连即可 |

## 工作原理

插件**不使用、也不需要**你的微博账号 Cookie。m.weibo.cn 的时间线接口要求一个"游客身份"，插件会自动向微博游客系统（`visitor.passport.weibo.cn`）完成经典的 `genvisitor → incarnate` 流程，把匿名游客 Cookie（SUB/SUBP，种在 `.weibo.cn` 域）维护起来，整个过程无需登录、无需人工干预：

1. 首次请求前自动预热 `m.weibo.cn` 并换取游客身份（本机实测可拿到 `ok=1` 的正常数据）；
2. 每轮向 `https://m.weibo.cn/api/container/getIndex?type=uid&value={uid}&containerid=107603{uid}` 请求第一页微博；
3. 与本地已见 ID（`data/plugin_data/astrbot_plugin_weibo_monitor/state.json`）比对去重，新微博按「旧→新」顺序推送到所有绑定会话；
4. 遇到 `ok=-100` / HTTP 418/432（游客身份过期或风控）时自动换新游客身份并重试一次；游客身份最长复用 3 天，到期主动更新并持久化到本地。

## 已知限制

- 匿名游客身份大约可见 95% 的微博，**个别受限微博**（如仅粉丝可见、部分被限流内容）拉取不到，属于微博匿名访问的固有限制；如确需 100% 覆盖，可在配置里填写 `custom_cookie`（填写后插件改用该 Cookie 请求接口，失效时需自行更换）。
- 免 Cookie 方案依赖微博游客接口的稳定性，若微博调整反爬策略导致持续失败，请关注插件更新。
- 触发 IP 级风控（HTTP 432）时插件会自动进入全局冷却（最长 1 小时），期间不产生微博请求，属于预期的自我保护行为，可通过 `微博状态` 查看。
- 海外/VPS 部署的 IP 段更容易被微博风控，若频繁进入冷却，建议配置 `proxy` 走国内出口。
- 推送到多个群时，任一群成功即视为推送成功，不做按群粒度的重试。
- 群相册上传仅支持 NapCat 协议端（≥ v4.8.101）；纯视频微博不上传图片（群相册接口仅支持图片）；实况图转 GIF 需服务器安装 ffmpeg，否则改传封面静图。
- 相册上传失败不做自动重传（防止重复上传），缺失图片可用相册类插件对单条微博链接手动补传。
